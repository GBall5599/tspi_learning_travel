# 2026-08-03 学习记录：第 8 课当前 Buildroot 显示链路只读盘点

## 一、学习目标

在不接入屏幕、不烧录镜像、不修改设备树和未知 GPIO 的前提下，观察泰山派 RK3566 当前 Buildroot 的显示子系统，区分设备树描述、驱动绑定、用户态接口和物理连接状态。

## 二、当前显示链路结论

```text
内存中的画面
  → VOP（读取、组合和处理像素）
  → HDMI 或 MIPI-DSI（按对应协议传输）
  → 实际显示器 / Panel
```

当前实际确认的是：

```text
VOP：设备树启用，驱动已绑定
HDMI：设备树启用，驱动已绑定，但连接器 disconnected
MIPI-DSI0 / DSI1：设备树节点存在，但 status = disabled
Panel / 背光：未确认到已启用并工作的完整链路
```

因此，只能确认 DRM、VOP 和 HDMI 控制器的基础驱动链已经建立，不能声称当前正在向 HDMI 或 MIPI 屏输出画面。

## 三、用户态接口

检查结果：

```text
/dev/fb*：不存在
/sys/class/graphics：不存在
/dev/dri/card0：存在
/sys/class/drm/card0-HDMI-A-1：存在
```

理解：

- 当前主显示系统使用现代 DRM 接口，不以传统 `/dev/fb0` 为主要接口；
- `card0` / `renderD128` 对应主显示 DRM；`card1` / `renderD129` 来自 NPU，不是另一路屏幕输出；
- `/dev` 主要提供程序访问设备的数据或控制入口；
- `/sys` 主要呈现内核设备模型、状态、拓扑和驱动明确开放的少量控制属性；
- 不能仅凭路径位于 `/sys` 就认为它一定可写。

## 四、HDMI 连接器状态

```text
status: disconnected
enabled: disabled
modes: 空
```

这里的 `status` 是 DRM 连接器根据驱动和硬件检测得到的运行状态，不是设备树中的 `status` 属性。

```text
设备树 status = okay       → HDMI 控制器允许被内核使用
DRM status = disconnected  → 当前没有检测到物理 HDMI 显示器
```

不能通过向连接器 `status` 写入 `connected` 来制造真实连接；该属性通常是只读检测结果。

## 五、运行时设备树

```text
/proc/device-tree -> /sys/firmware/devicetree/base
```

第一次直接对 `/proc/device-tree` 使用 `find` 没找到候选节点，是因为它是起始符号链接，而当时的 `find` 没有跟随该链接。改查真实目录后定位到：

```text
display-subsystem
vop@fe040000
hdmi@fe0a0000
dsi@fe060000
dsi@fe070000
```

关键属性：

`display-subsystem` 的 `status` 属性不存在；设备树中 `status` 缺省时通常按可用处理。

```text
vop@fe040000:
  compatible = rockchip,rk3568-vop
  status = okay

hdmi@fe0a0000:
  compatible = rockchip,rk3568-dw-hdmi
  status = okay

dsi@fe060000:
  compatible = rockchip,rk3568-mipi-dsi
  status = disabled

dsi@fe070000:
  compatible = rockchip,rk3568-mipi-dsi
  status = disabled
```

本板是 RK3566，但这里出现 `rockchip,rk3568-*` compatible 并不表示板卡识别错误；RK3566 与 RK3568 的这些显示硬件模块和驱动兼容关系可以共用对应 compatible。

设备树节点存在只说明系统中有这份硬件描述；还要经过内核加载 DTB、`compatible` 匹配驱动、驱动 probe/初始化、子系统注册以及实际硬件连接验证，才能判断设备是否真正工作。

运行时设备树目录是当前 DTB 的只读展开视图，不能直接把其中 DSI 的 `status` 文件从 `disabled` 改成 `okay`。正确修改路径是：

```text
修改 DTS / DTSI
  → 编译生成 DTB
  → 按启动流程部署 DTB
  → 重启
  → 用 dmesg、/sys、/dev 和实际硬件重新验证
```

即使源码中把 DSI 改成 `okay`，也只代表允许控制器参与初始化；要形成可用显示链，还需要正确的 VOP 路由、endpoint 图、Panel、供电、复位、背光、时序和对应驱动等配置。

## 六、驱动日志判断

成功证据：

```text
rockchip-drm display-subsystem: bound fe040000.vop
dwhdmi-rockchip ... Detected HDMI TX controller
rockchip-drm display-subsystem: bound fe0a0000.hdmi
[drm] Initialized rockchip ... for display-subsystem on minor 0
```

日志中也出现若干 `error`、`failed` 和不支持项，但后续仍然完成 VOP、HDMI 绑定和 DRM 初始化。因此不能看到一条错误就断定整个显示驱动失败，应继续综合检查：

```text
后续是否 bound / Initialized
/dev 是否出现设备入口
/sys 是否出现对应对象和状态
实际硬件功能是否正常
```

日志里的 MIPI CSI 属于摄像头输入链路，不是显示输出：

```text
CSI：摄像头 → SoC
DSI：SoC → 屏幕
```

## 七、endpoint 暂定认识

目前只要求建立以下印象：

```text
endpoint：设备图中的连接端点节点
phandle：设备树节点的引用编号
remote-endpoint：对端 endpoint 的 phandle
```

`compatible` 解决“设备节点由哪个驱动匹配”，endpoint 图解决“硬件模块之间如何连接”。本课不要求熟练解析端口方向和所有编号；该知识点已记录，后续设备树进阶课程结合真实 DTS 和 binding 重新学习。

## 八、Shell 命令认识

已经能够解释：

```sh
ls -l /dev/fb* 2>/dev/null || echo '未发现 /dev/fb*'
```

含义：

1. 尝试列出所有名字以 `/dev/fb` 开头的路径；
2. `2>/dev/null` 丢弃错误输出；
3. 左侧命令失败时，`||` 执行右侧提示。

本课还接触了 `echo`、`ls`、通配符、变量、引号、`for`、`if`、`find`、管道、`grep`、`tr`、`od`、输入重定向和续行符。这些命令以能结合本次输出理解为目标，不要求一次背熟。

## 九、问答验收

已能够大致说明：

- VOP、HDMI/MIPI-DSI 和 Panel 的职责；
- 设备树节点存在不等于真实硬件正在工作；
- `compatible`、设备树 `status`、probe、bound、DRM 初始化之间的关系；
- `/dev`、`/sys`、`dmesg` 分别用于观察什么；
- 当前泰山派为什么有 DRM、VOP、HDMI，却没有正在工作的显示输出；
- `/sys` 属性只有在驱动明确提供写操作、权限允许且值合法时才能用于控制设备；其修改通常只是运行时状态，重启后不保留。

需要继续巩固：

- endpoint / phandle / remote-endpoint 的真实 DTS 图；
- sysfs 属性的只读/可写权限和驱动实现之间的关系；
- DSI、Panel、背光和触摸组成完整 MIPI 屏链路的细节。
