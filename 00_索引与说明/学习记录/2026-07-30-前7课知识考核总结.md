### 3.3 第 3、4 课：Shell、权限与持久化

| 考核知识点 | 结论 |
|---|---|
| `sh /userdata/hello.sh` 与直接执行脚本 | ✅ 知道前者显式由 `sh` 解释，不要求脚本可执行；后者需要执行权限，并通常依赖有效 shebang。 |
| `$?`、`$#`、`$1` | ✅ 知道 `$?` 是上一条命令退出状态，`0` 通常代表成功；能正确判断 `./hello.sh ssh` 时 `$#=1`、`$1=ssh`，无参数时 `$#=0`、`$1` 为空。 |
| `chmod +x` | ✅ 知道其增加执行权限；仅可读的脚本不能直接作为可执行文件启动，但可交给 `sh` 读取执行。 |
| `/tmp`、`/etc`、`/userdata` | ✅ 知道 `/tmp` 是重启通常丢失的临时数据，`/etc` 用于系统配置，用户实验文件应优先放入 `/userdata`。 |
| `sync` | ✅ 知道它将尚未落盘的脏数据尽快写入存储，以降低重启/掉电前的数据丢失风险；它不是让配置自动立即生效的命令。 |

### 3.4 第 5 课：GPIO、按键与 LED

| 考核知识点 | 结论 |
|---|---|
| GPIO 全局编号 | ✅ 能按旧 sysfs 规则计算：`base + line offset`；例如 `96 + 5 = 101`。 |
| 物理 Pin 与 Linux GPIO 编号 | ✅ 知道排针位置不等于 Linux GPIO 号；排针还可能是电源、地或复用为 UART/I2C/SPI，需结合 GPIO bank、line offset 与 pinmux。 |
| `/dev/gpiochip*` | ✅ 知道它们是 GPIO 控制器设备节点，不是单独的 GPIO 引脚编号。 |
| LED 子系统优先级 | ✅ 知道优先用 `/sys/class/leds/rgb-led-r/`，由驱动处理有效电平、资源申请与 trigger，避免直接导出 GPIO 造成冲突。 |
| 字符设备与块设备 | ✅ 经讲解后能正确分类：`/dev/input/event4` 是字符设备，`/dev/mmcblk0` 是块设备；前者偏数据流/硬件交互，后者偏块存储/文件系统。 |
| `adc-keys` 与 `KEY_RESTART` | ✅ 已补强：`adc-keys` 读取 ADC 电压区间并上报 input 事件；`00 00 01 98` 是 32 位值 `0x00000198`，十进制为 `408`，对应 `KEY_RESTART`。 |

### 3.6 第 7 课：设备树入门

#### A. 源码、二进制、运行时视图与驱动链路

```text
DTS / DTSI（源码）
  → DTB（编译后的二进制设备树）
  → 启动加载器交给 Linux 内核
  → /proc/device-tree（当前运行时只读设备树视图）
  → compatible 匹配驱动并成功 probe
  → /sys、/dev 等用户态接口
```

考核结论：✅ 已能区分 DTS/DTSI、DTB 与 `/proc/device-tree`；知道 `/proc/device-tree` 不能直接修改，也不能可靠反推出原始 DTSI 的包含关系。

#### B. 节点、属性与字符串读取

| 考核知识点 | 结论 |
|---|---|
| 节点与属性 | ✅ 知道 `/proc/device-tree/leds` 这类目录表示节点，`/proc/device-tree/model` 这类文件表示属性。 |
| NUL 分隔字符串 | ✅ 知道 `compatible` 的多个字符串以 NUL（`\0`）分隔，直接 `cat` 时可能连在一起；可用 `tr '\0' '\n'` 辅助阅读。 |
| `model` 与 `compatible` | ✅ 已巩固：`model` 主要供人识别板卡；`compatible` 主要供内核/驱动匹配。 |
| 多个 `compatible` 字符串 | ✅ 知道通常按“具体板卡 → 通用 SoC”排列，便于优先具体匹配、再回退到通用匹配。 |

#### C. LED、按键与用户态接口

| 考核知识点 | 结论 |
|---|---|
| `compatible = gpio-leds` | ✅ 知道它是内核驱动匹配依据，而不只是“节点类型说明”。 |
| `linux,default-trigger = timer` | ✅ 知道 LED 驱动创建 `rgb-led-r` 时设定默认 trigger，用户态可通过 `/sys/class/leds/rgb-led-r/trigger` 查看或切换。 |
| 设备树与驱动分工 | ✅ 知道设备树自身不直接控制 GPIO；必须由匹配的 `gpio-leds` 驱动解析节点、初始化成功后，才会创建 `/sys/class/leds/rgb-led-r/`。 |

#### D. `chosen/bootargs` 与修改流程

| 考核知识点 | 结论 |
|---|---|
| `chosen/bootargs` | ✅ 已补强：它最终作为内核命令行影响根文件系统、控制台、`earlycon` 等启动行为。最终运行时视图不记录逐项来源，不能断言每个字段都由 U-Boot 单独生成。 |
| 修改 LED 默认 trigger 的正确流程 | ✅ 能说明应修改 DTS/DTSI 源码、重新生成 DTB、部署到实际启动链加载的位置并重启；通过 `/proc/device-tree/...` 和 `/sys/class/leds/.../trigger` 双重验证。 |

## 四、本次纠正和需要记住的边界

### 已完成纠正

1. `adc-keys` 上报的是 input 事件，`label` 是名称/描述，不等于“按下时打印 label”；
2. `sync` 的含义是尽快落盘，不等于配置立即生效；
3. `/proc/device-tree` 是内核的运行时只读视图，不是“可编辑的编译后 DTB 文件”；
4. 设备树节点存在不等于用户态接口必然存在，还需要匹配的驱动成功初始化；
5. `compatible` 是驱动匹配依据，`model` 主要供人阅读。

### 暂不纳入本阶段的进阶内容

“设备树节点存在但 `/sys/class/leds/...` 不存在”的完整排障，需要进一步学习：内核配置、驱动加载、内核日志、GPIO/pinmux、资源冲突和 probe 失败分析。本次不作为第 7 课基础掌握的判定条件。
