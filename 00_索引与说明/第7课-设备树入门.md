# 第 7 课：设备树入门——从运行中的 DTB 观察 LED、按键与启动参数

> 完成日期：2026-07-29
> 目标板：LCKFB-TSPI-RK3566-2G-16G
> 板端系统：Buildroot 2024.02 + Linux 6.1.141 aarch64
> 本课原则：全程只读观察，不修改 DTS、DTB、GPIO、LED 或启动参数。

## 1. 本课目标

理解设备树在启动和驱动绑定中的基本作用，并从当前运行系统验证以下链路：

```text
DTS / DTSI 源文件
  → DTB 二进制设备树
  → 启动加载器将 DTB 交给 Linux 内核
  → 内核解析硬件节点并匹配驱动
  → 创建 /sys、/dev 等用户态接口
```

## 2. DTS、DTSI 与 DTB

| 名称 | 含义 | 是否可直接阅读 |
|---|---|---|
| DTS | Device Tree Source，设备树源文件，通常描述某块具体板卡 | 是 |
| DTSI | Device Tree Source Include，可被多个 DTS 引用的公共片段，常用于 SoC 或共用外设描述 | 是 |
| DTB | Device Tree Blob，由 DTS/DTSI 经 DTC 编译得到的二进制设备树 | 否，通常需反编译或由内核导出后查看 |

`/proc/device-tree` 不是原始 DTS 源码目录，而是 Linux 内核从当前 DTB 建立的只读设备树视图。DTSI 的“包含关系”已经在编译为 DTB 时展开，因此不能从该运行时目录直接看出某个属性原本来自哪个 DTSI 文件。

## 3. 节点与属性：如何区分目录和文件

不能依据名称中是否带 `@` 判断。`@` 后常是硬件寄存器基地址，例如 `serial@fdd50000`，但它不是目录标志。

可靠方法：

```sh
ls -ld <路径>
```

最左侧字符含义：

| 首字符 | 含义 | 在设备树中的意义 |
|---|---|---|
| `d` | 目录 | 设备树节点 |
| `-` | 普通文件 | 设备树属性 |

实测：

```text
drwxr-xr-x ... /proc/device-tree/leds
-r--r--r-- ... /proc/device-tree/model
```

所以：

```text
/proc/device-tree/leds  → 节点目录
/proc/device-tree/model → 属性文件
```

根节点 `model` 内容为：

```text
lckfb tspi V10 Board
```

设备树字符串以 NUL 字节结束，通常没有普通文本的行尾换行，因此 `cat` 的输出可能与 shell 提示符连在一起。

## 4. 根节点兼容字符串

执行：

```sh
tr '\000' '\n' < /proc/device-tree/compatible
```

结果：

```text
lckfb,tspi-v10
rockchip,rk3566
```

`compatible` 列表通常从更具体到更通用：

1. `lckfb,tspi-v10`：具体板级兼容标识；
2. `rockchip,rk3566`：RK3566 SoC 级兼容标识。

内核可据此为节点选择兼容的驱动或板级处理逻辑。

## 5. LED：设备树到 sysfs 的验证

根节点下发现：

```text
leds/
```

其父节点属性：

```sh
cat /proc/device-tree/leds/compatible
```

结果：

```text
gpio-leds
```

子节点包括：

```text
rgb-led-r/
rgb-led-g/
rgb-led-b/
```

验证红色 LED 节点：

```text
/proc/device-tree/leds/rgb-led-r/
```

其属性中存在：

```text
gpios
linux,blink-delay-off
linux,blink-delay-on
linux,default-trigger
```

读取：

```sh
cat /proc/device-tree/leds/rgb-led-r/linux,default-trigger
```

得到：

```text
timer
```

再读取内核 LED 子系统接口：

```sh
cat /sys/class/leds/rgb-led-r/trigger
```

结果中包含：

```text
[timer]
```

方括号表示当前生效触发器。由此验证：

```text
leds compatible = "gpio-leds"
  → 内核 gpio-leds 驱动解析 rgb-led-r/g/b 子节点
  → 创建 /sys/class/leds/rgb-led-r/g/b
  → 当前红色通道使用 timer 触发器
```

`gpios` 属性是二进制引用信息，包含 GPIO 控制器、line、标志等，不应简单视为一个单独的 Linux GPIO 全局编号。

## 6. REC 按键：设备树到 input 事件的验证

根节点下存在：

```text
adc-keys/
```

该节点属性包括：

```text
compatible
io-channels
io-channel-names
keyup-threshold-microvolt
poll-interval
restart-key/
```

读取：

```sh
cat /proc/device-tree/adc-keys/compatible
```

结果：

```text
adc-keys
```

`restart-key/` 是具体按键子节点，包含：

```text
label
linux,code
press-threshold-microvolt
```

读取标签：

```sh
cat /proc/device-tree/adc-keys/restart-key/label
```

结果：

```text
restart
```

`linux,code` 是设备树二进制数值，使用十六进制查看：

```sh
hexdump -C /proc/device-tree/adc-keys/restart-key/linux,code
```

结果：

```text
00000000  00 00 01 98  |....|
```

设备树数值为大端序：

```text
0x00000198 = 408
```

第 5 课中 `evtest /dev/input/event4` 已实测：

```text
Event code 408 (KEY_RESTART)
```

完整链路：

```text
adc-keys / restart-key
  → compatible = "adc-keys"
  → linux,code = 408
  → 内核 adc-keys 驱动
  → /dev/input/event4
  → KEY_RESTART（408）
```

## 7. chosen 与启动参数

`/proc/device-tree/chosen/` 中存在 `bootargs`。它保存当前内核收到的启动参数。

实测参数包含：

```text
storagemedia=emmc
rw rootwait
earlycon=uart8250,mmio32,0xfe660000
console=ttyFIQ0
root=PARTUUID=614e0000-0000
androidboot.fwver=...uboot-250929
```

含义：

- eMMC 是启动存储介质；
- `rootwait` 使内核等待根存储设备就绪；
- `earlycon` 和 `console=ttyFIQ0` 解释了早期内核日志和调试串口控制台；
- `root=PARTUUID=...` 指定根文件系统分区；
- `androidboot.fwver` 记录 DDR、BL31、BL32、U-Boot 等固件标识。

启动流程应理解为：

```text
BootROM / 前级固件
  → U-Boot
  → 内核 + DTB + 最终启动参数
  → Linux 内核解析 DTB
  → 内核匹配驱动并挂载根文件系统
```

`chosen/bootargs` 证明内核最终收到这些参数；仅凭该文件不能判定每一项必然由 U-Boot 在运行时单独写入，它们也可能来自 DTB 预置内容或由加载器补充、覆盖。

输出中的 `#li-03/20/2026` 是厂商构建标记，日期为 2026 年 3 月 20 日，不是当前系统时间。
