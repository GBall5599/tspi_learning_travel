## 1. 项目定位

本项目以立创·泰山派 RK3566 的官方“胖妞智能小手机”项目为目标，但不直接从 Android 补丁或外观组装开始。

采用两阶段实施：

```text
阶段 A：Linux / Buildroot 最小可用版
  → 屏幕、背光、触摸、按键、LED、Wi-Fi 状态和自启动

阶段 B：官方 Android 完整版（可选进阶）
  → 横竖屏、Logo、开机动画、桌面 / 预装应用、系统镜像构建
```

阶段 A 是正式主线；阶段 B 必须在显示、触摸、设备树、SDK 和内核驱动链路均已稳定后才开始。

### 2.3 已知硬件匹配风险

当前 D310T9362V1 本地资料表明：

```text
面板分辨率：480 × 800
面板驱动：ST7701S
触摸 compatible：hyn,cst128a
触摸 I2C 地址候选：0x38 或 0x48
```

官方“胖妞”项目的补丁批次中还存在不同触摸实现和 GP7101 背光方案。因此，**必须以自己手中的屏幕实物、排线、转接板、触摸 I2C 地址和当前 SDK 为准，不能混用不同批次补丁。**

另外，本地 D310 补丁的旧源码基线为 `tspi_linux_sdk_20230916`，而当前已下载 SDK 为 kernel 6.1、2026-04-03 版本。旧补丁不能直接对新 SDK 执行 `patch`；必须先比较目录、设备树节点、内核配置和驱动接口，再选择移植或重写。

## 4. 实施阶段 A：Linux / Buildroot 最小可用版

### P0：实物与资料兼容性核对

目标：建立本项目的“硬件事实表”，不修改系统。

核对项：

- 屏幕是否确为 D310T9362V1；
- 面板分辨率和方向是否为 480 × 800；
- 屏幕 FPC、转接板、排线方向、供电和固定方式；
- 触摸芯片及实际 I2C 地址到底是 `0x38` 还是 `0x48`；
- 背光是 SoC PWM 直驱还是 GP7101 I2C 背光；
- 当前硬件是否具备官方项目所需的扩展板、音频和外观结构条件；
- 当前 Buildroot 镜像、串口参数与恢复镜像的位置。

验收：完成一张带照片、型号、接口、地址和恢复方式的硬件事实表。

### P1：官方镜像显示基线

目标：使用已经下载的官方 3.1 寸 MIPI Debian 镜像确认硬件基线。

验证：

```text
系统启动
→ 屏幕点亮
→ 分辨率 / 方向 / 颜色正确
→ 背光正常
→ 触摸产生 input 事件
→ 串口、网络、SSH 正常
```

验收：保存串口日志、屏幕照片、触摸事件记录和与当前 Buildroot 的差异表。

### P2：匹配 SDK 中的 MIPI 面板

目标：在匹配的 kernel 6.1 SDK 中定位并配置正确的 DSI、panel、时序和初始化序列。

标准流程：

```text
备份原始源码与可启动镜像
→ 对比官方补丁、D310 补丁和当前 SDK
→ 只移植显示相关的必要改动
→ 编译 DTB / 内核或完整镜像
→ 串口观察启动
→ 验证 /proc/device-tree 与 framebuffer / DRM
→ 无法启动时按既定路径回退
```

验收：Buildroot 或匹配 Linux 系统下屏幕稳定点亮，且显示配置来源可追溯。

### P3：背光与触摸驱动

目标：分别完成背光和触摸，不将两个问题混在一起排查。

背光链路：

```text
硬件类型确认（PWM 或 GP7101）
→ 设备树节点
→ 驱动 probe
→ 用户态亮度接口
→ 最小亮度 / 最大亮度 / 重启后默认状态验证
```

触摸链路：

```text
I2C 总线与地址确认
→ compatible 与驱动匹配
→ reset / interrupt GPIO 确认
→ 驱动 probe 日志
→ /dev/input/event* 出现
→ evtest 验证坐标、方向和多点触摸
```

验收：背光可控；触摸坐标与显示方向一致；重启后可稳定恢复。

### P4：Linux 版“胖妞”用户态应用

目标：在已经可用的显示和输入链路之上，写出自己的最小应用，而不是直接依赖 Android。

分版本实现：

```text
V1：屏幕显示“系统正常启动”
V2：显示时间、IP、Wi-Fi 状态、CPU 温度
V3：REC 按键和触摸切换页面
V4：RGB LED 指示网络和程序状态
V5：开机自启动、日志记录、异常退出后的恢复策略
```

建议目录：

```text
06_项目案例/胖妞智能小手机/
  ├─ app/         主业务与页面状态机
  ├─ platform/    显示、按键、LED、网络状态的统一接口
  ├─ scripts/     构建、部署、启动和日志收集
  ├─ docs/        接线、构建、烧录、恢复和验收记录
  └─ README.md    项目运行说明
```

验收：系统重启后应用可自动启动，屏幕、触摸、按键、LED 和网络状态可稳定联动。

### P5：外观、音频和整机集成（按需）

仅在 P0～P4 稳定后进入：

- 根据官方 BOM 和结构文件确认实际需要采购或制作的部件；
- 先不改板，优先使用官方或已验证的转接板与排线；
- 音频、外壳、供电与散热分模块验证；
- 最后才进行整机装配和长期运行测试。

验收：整机连续运行、触摸和显示稳定，且可通过串口恢复系统。

## 5. 实施阶段 B：Android 完整版（可选进阶）

开始条件：阶段 A 的 P0～P4 已稳定完成，并且已明确 Android 补丁对应的 SDK / 源码基线。

建议顺序：

```text
确认 Android SDK 版本与磁盘空间
→ 在 Ubuntu ext4 中准备完整源码
→ 建立干净基线并完成一次原始构建
→ 仅应用与当前硬件匹配的屏幕 / 背光 / 触摸补丁
→ 编译并烧录验证
→ 处理横屏 / 竖屏
→ 加入 Logo、开机动画、桌面或预装应用
→ 保存可恢复的原始镜像与最终镜像
```

禁止事项：

- 不在未完成 Linux 基线前进入 Android 大编译；
- 不将横屏和竖屏补丁叠加；
- 不把不同硬件批次的触摸、背光和面板补丁混用；
- 不在 Windows NTFS 共享目录中构建 Android SDK。

验收：系统稳定启动，显示、触摸和方向正确，定制资源生效，并保留可复现构建记录。

## 6. 风险、回退与版本管理

### 6.1 主要风险

| 风险 | 预防与处理 |
|---|---|
| 补丁与 SDK 年份 / 内核版本不匹配 | 先阅读 diff，再逐项移植；禁止盲目 `patch` |
| 屏幕能亮但触摸无效 | 将 MIPI、背光、I2C、GPIO 中断、input 分层排查 |
| 背光异常 | 先确认 PWM / GP7101 硬件方案，再修改设备树或驱动 |
| DTB 导致无法启动 | 保留原始 DTB / 镜像，串口观察并从已知镜像恢复 |
| Android 构建资源不足 | 提前预留 Linux ext4 磁盘空间，不在 Windows 共享盘编译 |
| 项目范围失控 | 以 P0～P5 的验收点推进，每次只解决一个层次的问题 |

### 6.2 每次改动前的最小检查清单

```text
[ ] 当前可启动镜像名称与位置已记录
[ ] 串口可用
[ ] 原始 DTS / 驱动 / 配置已备份或已提交 Git
[ ] 本次只改一个明确目标
[ ] 已定义验证方法
[ ] 已定义失败后的回退方法
```
